# RTL验证日志：真实三批 continuation 与可恢复执行

日期：2026-08-16

## 1. 目标与设计边界

本轮继续服务于既定 ASIC 加速器目标，主数据流保持：

`深度分组 → Gaussian 有序发射 → Gaussian 内部 8×8 block 遍历`

没有增加 per-tile bin、per-tile list 或 per-tile sort 主路径。动态 G/P/R/E 配置、global GID 属性地址和 AXI 通路语义均未改变。本轮修改集中在真实负载生成和验证 testbench，为完整 1,030 批帧建立可恢复执行基础设施。

全部训练场景、输入和输出只在 `D:/3DGS` 本地处理，没有上传网络，也没有安装或更新软件。

## 2. 属性输入生成器校准

为解决原环境缺 NumPy 的临时问题，曾实现纯标准库 C++ 属性生成器。batch 0 的 9,216 个属性 beat 中最初只有一个 scale 量化 bit 不同；修正半 LSB 后，batch 0 的四个输入文件与 Python 金标 SHA-256 完全一致。

继续用独立 Python 金标检查 batch 1 时，仍发现 5 个 scale LSB 差异。根因是不同数学库的单精度 `expf` 结果不能保证跨全部输入逐 bit 相同。因此：

- C++ 生成器明确降级为非签核工具，并在运行时输出 warning；
- 所有 RTL 签核输入统一由原 Python/NumPy 路径生成；
- 本机 Codex 隔离 Python 已包含 NumPy 2.3.5，无需联网或安装软件。

随后把 Python 生成器从“每批扫描完整 PLY”改为按 global GID 对 PLY memmap 做稀疏高级索引。batch 1 生成时间从约 5 分钟降低到 0.205 秒，四个输出文件与改动前逐 bit 一致：

- `mean.memh`: `0C30FB2B9BDAC36B35CDE3CA8F1087E2BC00DED95FDB179FB69CBA5AC2017486`
- `global_gid.memh`: `AF96263D4F1751AB0AB4D2F621ED18E0BD862DEF9E819A046A7B7140472094E8`
- `camera.memh`: `61FE2BD0C777D6522A5860BD8FF5DE1F9ABAF8C76723066DEC7EB15F66F2EADC`
- `attribute_sparse.memh`: `33F1CF656D849F511FA438187FDE2D3904B377603BE5C21A54443701DDBC847A`

规范生成脚本为 `scripts/prepare_full_frame_rtl_range.ps1` 和 `scripts/build_full_frame_rtl_batch.py`。

## 5. Checkpoint 语义边界

同一 Verilator 进程内的范围执行保留完整硬件状态，包括 epoch、framebuffer、像素/块 termination 状态和累计性能计数，适合最终连续性能签核。

跨进程 checkpoint 保存并恢复外部 128-bit framebuffer。重启后内部 termination cache/table 会清空并重新学习，因此：

- 固定点图像累积应逐 bit等价，已由小规模测试证明；
- 重启段的 cycles/skip 等性能计数不能拼接成“单次连续硬件执行”结果；
- 最终性能报告仍应使用同一进程连续范围执行；checkpoint 主要用于长时间数值闭环和故障恢复。

## 9. 必须保留的图像质量风险

协议、批间状态、计数和完整覆盖通过，不等同于图像质量通过。完整PNG仍近似灰色：

- nonzero pixels：2,752；
- RGB min：`[56,50,52]`；
- RGB max：`[74,88,92]`；
- T min/max：`0/7`。

而且前1,024颗后已经是T=1–7，前2,047颗后为T=0–7；说明像素非常早地饱和/终止，后续约百万Gaussian主要被early termination跳过。仅凭该PNG不得宣称图像质量正确，也不得给出虚假的ground-truth PSNR/SSIM/LPIPS。

随后对同一相机146、同一64×43分辨率、同一前1,024颗有序Gaussian运行独立软件浮点Gaussian-wise参考：

- 1,024颗中161颗与屏幕重叠；
- bbox面积中位数就是整幅2,752像素；
- 浮点模型也在首批使全部2,752像素达到early-termination阈值；
- 浮点图同样是缺少细节的平滑棕灰图，RGB min/max约为`[85,77,65]`/`[118,109,94]`。

因此，“首批全屏饱和且低细节”主要是64×43低分辨率、近层Gaussian巨大投影footprint和early termination共同造成，不是RTL独有错误。完整RTL与batch0图逐bit相同，也是该顺序/终止合同的直接结果。

但RTL batch0相对这张内部浮点参考仍只有：

- PSNR：18.222 dB；
- SSIM：0.884；
- LPIPS：不可用。

该指标仅是算法内部诊断，不是原始照片ground truth。它证明RTL颜色/alpha/blend定点链仍存在明显数值偏差，需要继续定位；同时也否定了“灰图一定意味着RTL控制错误”的过强结论。

下一轮第一优先级应转为数值质量定位：逐级对照浮点/定点SH颜色、alpha和blend；projection/bbox导致的首批全屏覆盖已被浮点模型复现，但其定点误差仍应量化。当前本地数据目录没有Bonsai原始参考PNG；隔离Python有NumPy/Pillow但没有torch/lpips。因此：

- 可先用软件浮点/定点模型做内部逐级差异定位；
- 最终PSNR/SSIM需要相机146对应的原始参考图，或明确认可的软件浮点渲染金标；
- LPIPS还需要经用户确认准备离线torch/lpips及权重；
- 在质量风险关闭前，不进入最终PPA结论阶段。
