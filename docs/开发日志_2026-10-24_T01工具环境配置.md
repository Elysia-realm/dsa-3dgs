```powershell

```

在 Ubuntu 中：

```bash

iverilog -V
verilator --version

```

`~/.bashrc` 已加入加载 `~/eda/env.sh` 的一行；新的交互式 Bash 会加载。非交互脚本应显式 source。原 `.bashrc` 已保存到证据目录。

## 4. 实装发现的问题及处理

### GitHub Git 下载失败

WSL 的 Git 直连失败，保留 `logs/cudd-clone.log`。改从官方 `codeload.github.com` 下载源码归档，通过归档 PAX 中的提交号与 SHA-256 固定版本，未换用未知来源二进制。

| 工具 | 实际源码提交 |
|---|---|
| CUDD | `f54f533303640afd5dbe47a05ebeabb3066f2a25` |
| OpenSTA | `2b5a1181a7293e62c0ba513004238c8c3a048ab3` |
| CACTI | `1ffd8dfb10303d306ecd8d215320aea07651e878` |
| Ramulator | `214f635845214adf030367939655d172ef0fed5f` |

源码包保存在 `tmp/toolchains/linux_sources_20261024`，哈希见 `source_archives.json`。OpenSTA 启动横幅显示 `GITDIR-NOT` 是归档构建没有 `.git` 目录，实际提交从上述归档记录追溯，不能把该横幅当作未知版本。

WSL 启动仍提示 Windows localhost 代理未镜像。apt/pip 可访问，已安装工具可离线运行；不宣称 GitHub Git 直连已经恢复。未修改代理、安全策略或防火墙。

### 活动标注为零

原冒烟脚本用 Verilator 覆盖了 Icarus 的 `smoke.vcd`，但使用 Icarus 的 `tb/dut` scope。Verilator 多一层 `TOP`，首次实际结果是 `Annotated 0 pin activities`，因此首次功耗读取不能视为有效活动通过。

现在分别保存 `smoke-icarus.vcd` 和 `smoke-verilator.vcd`，为 STA 明确选择 Icarus VCD，并增加非零活动标注检查。新结果为 **11 个引脚活动**，功耗报告有实际活动输入。原失败证据留在 `smoke/`，接受的结果位于 `smoke-v2/`。

小测试 max slack=4.16ns、min slack=-0.25ns。它没有插入 hold 延迟，0.25ns uncertainty 下有明确 hold 违例。这里验证工具能计算和报告违例，不宣称此小电路时序签核，更不代表加速器时序情况。

### Ramulator 编译兼容性

原 Makefile 默认 `clang++`，本次环境使用 GCC；指定 `CXX=g++` 后又暴露原源码依赖传递包含提供 `uint64_t`，GCC13 下失败。最终使用：

```bash
make CXX=g++ CXXFLAGS='-O3 -std=c++11 -g -Wall -include cstdint' -j4
```

不修改上游源码。两次失败及接受构建日志分别保留。官方五请求 LPDDR4 trace 已实际运行，仍不是 AXI 闭环或真实负载验证。

### CACTI 原样例输出 inf

上游 `io.cc` 使用了 `ron_value/rtt_value/tflight_value`，但配置解析没有读取它们；原 `cache.cfg` 的 tflight 数值也缺失，导致 DDR3 I/O 面积 `inf`。仅改成 LPDDR2 预设会触发 MemCAD 只接受 DDR3/DDR4 的断言，因此该尝试也记为失败，没有采用。

最终采用一个明确归档的本地配置解析修复：初始化三个值为无效哨兵；解析并检查三个输入；缺失或非法时返回错误。只修改 `io.cc` 的配置处理，没有修改 SRAM 面积/延迟/能耗算法。

- 补丁：`cacti_config_parser.patch`。
- 前后哈希：`cacti_patch_manifest.json`。
- 原源码：`cacti-io.cc.before`；源码目录原二进制：`cacti.upstream`。
- 接受配置：`cacti_sram_diagnostic.cfg`，使用实际解析器支持的 `-dram type` 语法，显式设置辅助 DDR3 I/O 参数。
- 正向检查：64KiB、128bit、1RW、通用45nm、300K、无ECC SRAM 的输出全部为有限数值。
- 负向检查：原样例缺 tflight，明确失败，日志为 `logs/cacti-invalid-config.log`。

诊断访问时间0.504959ns、周期0.795423ns、读能量0.0332256nJ、写能量0.0287556nJ、bank漏电29.3685mW。它们只属于该诊断配置，不能填入项目实际SRAM预算。辅助DDR3输出也不是本项目LPDDR4能耗/时序模型。

### Windows 应用程序控制阻塞

`pacman` 成功安装包括 UCRT64 Python 在内的16个包，安装前后清单均保留。但 Windows 启动 `cygpath.exe` 报“应用程序控制策略已阻止此文件”，Python 启动退出码为 `-1058471934`。因此不能把依赖安装完成当作 Windows 新构建通过。

继续核查已从 `Microsoft-Windows-CodeIntegrity/Operational` 取得与这些程序相关的3033/3077事件；3077明确记录执行被策略阻止，相关记录保存在 `windows_code_integrity_events.json`。该事件含义与[微软应用控制事件说明](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/operations/event-id-explanations)一致。

没有关闭、放宽或绕过系统策略。若继续使用原 Windows/MSYS2 构建流程，需要用户/设备管理员按本机应用控制策略处理；也可在后续任务中正式移植回归脚本到已验证的 Linux 环境。原脚本硬编码 Windows 路径，尚未完成此移植，不能说现在可直接原样运行。
