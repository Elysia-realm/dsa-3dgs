# T04 最终 RGB 帧输出签核

日期：2026-10-05  
状态：原签核重开后，五场景同版本验证完成，现已重新签核；原记录与修正保留如下

## 本轮关闭的验收项

生产顶层不再把 RGB/T/epoch 内部状态误作成品图像。新增帧末 RGB DMA，在最终
continuation 批次的计算、状态读和状态写全部排空后，逐像素读取 scratch：当前 epoch
执行背景合成，旧 epoch/未触及像素直接采用背景；随后将 Q12 颜色饱和量化为 RGB888。

输出格式冻结为 R/G/B 字节顺序、行优先、`align16(width*3)` 行跨度和零填充。默认背景为
黑色。内部 scratch 放在最终图像之后，避免成品 RGB 覆盖 epoch 标签。写 DMA 使用最多
15 个 128-bit beat 的 INCR burst，并在 4 KiB 边界拆分。系统 DONE、done IRQ 和
`frame_done_pulse_o` 均等待最后 B 响应；配置、读和写错误分别进入状态 bit22–24。

主机示例 `scripts/read_rgb888_frame.py` 只读取 RTL DMA 字节并封装 PNG，不再从内部状态
重算背景、量化或渲染。

## 边界与停止决定

原记录将定向 DMA 与空帧系统联调视为足以关闭 T04。用户复核后发现，这无法证明非空真实
负载、状态写回与最终 RGB 扫描在生产顶层协同正确，原完成结论撤回并重开。真实数据输出
验证必须满足五场景最低覆盖；全场景、目标分辨率、GT 指标仍由 T10 验收。
RGBA、视频接口、运行时背景选择及继续扫描 burst 深度的收益不构成 T04 硬性缺口，按停止
规则冻结，不再投入低收益优化。

下一项：T05，正式 G/P/R 共享资源与 Bitonic 组内精排配置。

## 用户复核后的修正（2026-10-05）

1. 原 `tb_real_dma_workload` 固定 `USE_FINAL_RGB_DMA(0)`，因此完整回归中的真实负载没有
   经过最终 RGB DMA。原定向测试生成的向量与 1×1 空帧不足以形成真实场景输出验收证据。
2. 发现顶层 multiwrite 与 writethrough 分支未隔离 RGB 阶段的 `BVALID`。multiwrite 在
   outstanding=0 时看到 RGB B 响应会置状态写回错误。修复这两个连接，并在系统相机测试
   的正常最终帧后检查 `frame_error_o` 和 `write_error`，避免漏掉该失败。
3. `frame_busy_o` 纳入 `core_frame_done`，覆盖计算完成到 completion_pending 锁存间的一拍，
   使 continuation 软件轮询不会在输出扫描启动前误判空闲。
4. 新增真实 RGB 测试配置、可处理 burst 的外存模型、独立 RGB 字节转储与复现脚本。
   仿真把 scratch 放在 `OUTPUT_BASE + align16(width*3)*height`；最终 RGB 从真实 AXI W
   握手捕获，PNG 只做字节封装。scratch 仅供独立比较，不用于替换输出图像。
5. 原广泛 Python 结构测试曾有一项 T01 README 文本断言失败；它未在本轮修改，与 T04
   无关。原“失败 0”只适用于所列定向套件，不能表述为全部 Python 测试通过。

## 重新验收结果与最终范围

暂停期间后台测试已经完成。恢复后核对真实报告中的 79 个源码 SHA-256，全部匹配当前文件，
因此复用这组同版本证据。共五场景、十次 RTL 执行，各场景均使用 8,192 个从本地 PLY
确定性抽样的 Gaussian；相机取 cameras.json 的中间索引。固定 G 模式、4 lanes、2-entry
state window、2 MSHR、4096-entry cache、默认 multiwrite 深度 8；group/sort 容量为 128。
主机按量化 `(depth,GID)` 排序并生成 64 个 128-entry continuation 批次，pivot 均为 0，
正深度项进入同一组。该测试资源配置写入 `verification/rtl/build_t04_real_rgb.cmd`，不改变
生产顶层默认排序容量，不把此软件排序协议计为 T06 硬件自主调度。
