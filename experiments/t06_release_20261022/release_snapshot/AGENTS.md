# 项目执行与签核纪律

开始任务前阅读 `docs/毕业设计剩余任务执行清单_2026-09-20.md`、
`verification/implementation_status.json` 和对应任务最新日志。

## T04 教训：真实验证不足不得签核

用户明确要求纠正此前将局部测试、空帧联调及关闭新增功能的真实负载回归误当作完整验收的
问题。这是后续所有任务的持久约束。

- 区分“开发基本完成”“验收进行中”“完成并签核”。开发停止不等于验收通过；任何必需
  证据缺失、测试未执行或失败未闭环时，不得勾选完成或设置 `signed_off=true`。
- 对影响输入、计算、排序、调度、压缩或图像输出的任务，真实数据端到端验证是必需项，
  不能通过仅采用合成向量或将真实验证推到 T10 来免除。协议/模块测试仍须覆盖必要边界。
- 必须确认被验收功能在测试配置中实际启用，真实经过生产顶层与正式输入输出接口；用
  事务、计数、状态或输出证据证明路径执行。默认关闭、旁路或测试台替代不能作为该功能通过证据。
- 真实验收至少覆盖 `data` 中 5 个不同场景，同版本、同口径、所选全部通过。报告必须列明
  场景、相机、Gaussian 数量、是否完整集合、分辨率、参数/开关、软件预处理、逐次结果和失败项。
  五场景是最低覆盖，不保证任务所有条件已满足；正式完整范围仍按 T00/任务合同。
- 开始测试前明确本任务的验收条件与负载范围；逐条关联到实际证据后才能签核。抽样、低分辨率、
  单模式或局部比较不能冒充完整场景、目标画质、性能或硬件自主执行通过。
- 图像来自 RTL RGB DMA；PNG 只允许封装输出字节。验证错误状态、完成/IRQ 与最终事务排空，
  检查成品文件与 DMA 转储一致。观察图像异常并记录，不以有文件或输出非空代替正确性。
- 同一渲染实现的不同排序路径可能共享几何/颜色错误，RGB一致不能单独证明图像语义正确。
  T06暴露的近似纯色问题须以独立数学参考和原始字段布局核验闭环；不得仅归因于低分辨率。
- 多个DMA端口共享物理地址空间时，按完整负载检查所有输入、暂存和输出区域互不重叠；
  测试台分端口数组不得掩盖地址别名，并须检查实际事务的区间边界。
- 保留命令、配置、日志、输入/源码哈希与输出；仅复用源码及配置匹配的证据。明确未跑、失败
  和范围外检查，不笼统报告“失败 0”。发现旧签核证据不足时，重开并保留原因和原记录。
- 低收益停止规则只约束可选优化，不能削减必要验证或豁免正确性缺陷。达到本任务冻结条件后
  停止扩展，推进剩余主任务。

上述规则由执行清单中的“签核前强制证据门槛”细化；不改变 T00 目标和 T10 正式验收范围。

## 每次签核必须记录性能并闭环瓶颈（2026-10-18用户要求）

- 2026-10-18晚用户要求：后续开发测试暂不运行Kitchen、Garden，保留历史证据，不把暂缓
  当作最终免验；本轮以Bonsai、Counter、Room、Train、Truck保持至少五场景。T00最终13场景
  及30FPS合同不变。优化后须验证截至T06的全部已实现能力，不能只验证新增候选。

- 自T06起，每次任务签核测试必须归档主要性能指标与具体瓶颈分析，不能只报告功能PASS。
  记录整帧周期及计时边界、阶段工作/忙碌/背压/等待、G/P/R服务与争用、QSU划分/叶子填充、
  各DMA读写事务及字节、合成提交/缓存行为；缺失指标明确标记未测，不当成零。
- 仿真墙钟/主机CPU耗时、RTL周期、假定频率换算帧时/FPS及实测硬件性能必须分列。
  生产自主路径与CPU排序参考路径分别统计，不将参考验证成本算作加速器开销。
- 指标绑定场景/相机、完整或子集数量、分辨率、模式/开关、AXI配置、源码/输入哈希和原始日志。
  完整场景与低分辨率结果不能外推为T00目标分辨率/GT/30FPS已通过。
- 先冻结测试完成后的可信基线，再按证据排序具体瓶颈；busy不等于纯计算耗时，重叠计数不可相加。
  用有边界的对照/消融验证因果，不能凭单一计数盲目加并行或缓冲。
- 针对主要瓶颈做一次有依据、范围明确的优化与同条件前后对拍；遵循清单的本地文献优先规则，
  保留硬件自主输入、全局顺序、共享资源与正确性。改动后必须重新完成受影响的必要验收。
- 每轮记录优化收益、退化、资源代价和接受/回退/停止决定。约1%低收益停止规则仅适用于
  可选优化；未达到的硬指标必须保留并明确后续责任，不能通过停止优化宣称达标。
